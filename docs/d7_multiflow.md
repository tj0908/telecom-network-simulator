# D7：多流竞争与公平性分析

在 D1–D6 的单流实验基础上，D7 首次引入**多条流共享瓶颈**的场景：在
经典 dumbbell 拓扑上让两条 TCP 流与一条 UDP 流竞争同一瓶颈链路，
对比 FIFO 与 FqCoDel 两种队列策略在不同 UDP 干扰强度下的吞吐量、
时延、丢包与公平性。

程序 `src/multiflow_fairness.cc`，自动化脚本
`scripts/run_fairness_experiments.py`（含 7 项校验）、
`scripts/plot_fairness_results.py`。原有程序、结果与 14 项回归测试
未作任何修改，回归全部通过。

## 拓扑与参数（及选择依据）

```
 L0 ──┐                              ┌── S0
 L1 ──┼── R0 ════ 瓶颈 2Mbps ════ R1 ──┼── S1
 L2 ──┘        10ms 时延            └── S2
   接入链路 10 Mbps / 2 ms（双侧）
```

| 参数 | 取值 | 依据 |
|---|---|---|
| 瓶颈带宽/时延 | 2 Mbps / 10 ms | 与 D4/D5 相同，结果可跨天对照 |
| 接入链路 | 10 Mbps / 2 ms | 保证瓶颈只出现在中间链路 |
| 队列策略 | PfifoFast 100p / FqCoDel 100p | 容量相同、只换调度纪律（控制变量），与 D5 的 100p 场景衔接 |
| 设备队列 | DropTail 100p（两组相同） | 保留 D5 发现的双层结构，不人为移除 |
| 仿真时长 | 12 s，业务 1–11 s | 10 s 活动窗口比 D2–D5 的 8 s 更长，让竞争中的 TCP 流有时间进入稳态 |
| TCP 业务 | BulkSend，SendSize 1024 B | 与 D2–D4 一致 |
| UDP 业务 | OnOff 恒速，1024 B 包 | 速率是唯一随组变化的负载变量 |
| 随机种子 | ns-3 默认（固定） | 与此前各天一致，整矩阵复跑结果逐行相同（已校验） |

策略只施加在 R0→R1 出口方向（数据流方向）。反向 ACK 走对侧设备、
其队列未插桩——ACK 流量小且数据包丢弃绝大部分发生在正向瓶颈队列，
逐运行的对账（见下）也支持这一点；此为本实验的观测边界，特此注明。

## 实验矩阵与公平性定义

- 组 A：TCP×2，无 UDP；组 B：TCP×2 + UDP 500 kbps（瓶颈的 25%）；
  组 C：TCP×2 + UDP 4 Mbps（瓶颈的 200%，持续过载）。
- 每组各跑 FIFO 与 FqCoDel，共 6 组配置。
- **Jain 公平性指数** J(x) = (Σxᵢ)² / (n·Σxᵢ²)，取 x 为各流的
  IP 层吞吐量。D7 第一轮取 rxBytes×8 / 该流首包发送到末包接收的
  跨度（逐流跨度口径，与 D3 起的单流口径一致）；D7.1 审计发现该
  口径下各流分母不同、速率之和不可加总，且会把"到达时间分布"
  误读为"交付量公平性"，故新增**统一窗口口径**（同一运行内所有流
  共用 [最早 firstTx, 最晚 lastRx] 窗口）作为公平性结论的依据，
  逐流跨度口径保留为历史结果。两口径对照见文末审计一节。
  - 主指标 `jain_tcp`：只对两条 TCP 流计算（这才是同协议弹性流之间
    的公平性问题）。
  - 附带指标 `jain_all`：把 UDP 流也纳入。**局限性**：UDP 是恒速
    非响应流，不会因拥塞退让，它的"份额"不是拥塞控制协商的结果；
    把它和 TCP 放在同一公平性公式里，数值更多反映"UDP 占了多少"
    而非"分配是否公平"，只作参考，不作结论依据。

## 分析

**1. 无 UDP 或低速 UDP 时（A、B 组），两种策略的 TCP 公平性都接近
完美**（jain_tcp 0.9995–1.0000），吞吐分配也几乎一样。区别在时延：
FqCoDel 的平均时延比 FIFO 低约 40%（A：232 vs 382 ms；B：约 260 vs
约 440 ms）。**限定**：FIFO 与 FqCoDel 之差同时包含"按流分队列调度"
与"CoDel 式按排队时间丢弃"两个机制，D7 的设计无法把时延下降单独
归因于 CoDel；单流场景下同容量 FqCoDel 优于 FIFO 的证据在 D5。
吞吐公平在两条同构 TCP 流之间本来就不依赖队列策略。占用数据更
能说明机制差异：FIFO 的 qdisc 平均积压 50.9/56.5 包，而 FqCoDel 的
qdisc 平均占用只有 1.2/1.3 包（CoDel 把自身队列压得几乎为空）；
但两种策略下设备队列平均占用都在 82–89 包——FqCoDel 场景中几乎
全部站立排队都发生在它管不到的第二层，这正是时延只降约 40%
而非降到 CoDel 目标量级的原因（与 D5 的两层结论互相印证）。

**2. 高速 UDP 下 FIFO 发生经典的"非响应流饿死 TCP"**（C/FIFO）：
单一 FIFO 队列按到达比例丢弃，UDP 不退让、TCP 遇丢包退让，份额
螺旋式塌陷——按统一窗口口径，UDP 占走 1.9146 / 2 Mbps，两条 TCP
只剩 0.0283 与 0.0305 Mbps（10 秒内各只发出约 110 个包，基本处于
超时重传主导的停滞状态），**两条 TCP 同时遭受严重带宽挤压、且
程度相近**。**D7.1 审计修正**：第一轮用逐流跨度口径算出的
jain_tcp 0.7093 不能读作"两条 TCP 交付量不公平"——tcp1 的 38,916
字节集中在前 2.2419 s 内收到（lastRx=3.2419 s 后该流再无交付），
tcp2 的 41,856 字节则摊在 10.9934 s 里，两者交付量其实接近；
统一窗口口径的 jain_tcp 为 **0.9987**。跨度口径度量的是到达时间
分布差异，交付量公平性以统一窗口口径为准（详见文末审计一节）。

**3. FqCoDel 显著改善 TCP 的带宽份额**（C/FqCoDel）：按流分队列
调度后，UDP 的过量包主要被丢弃（其 lost 3690、未接收 75.58%；
丢弃发生在其 FqCoDel 子队列内是由逐流 lost 数字推得，未采集
子队列级计数，见结论边界 3），两条 TCP 的统一窗口速率回升到
0.5393 与 0.5402 Mbps，UDP 降到 0.9120 Mbps。
注意结论的准确表述：**TCP 之间的公平性在两种队列配置下都较高**
（统一窗口 jain_tcp：FIFO 0.9987 / FqCoDel 1.0000），FqCoDel 改变
的是 TCP 整体相对 UDP 的带宽份额，而不是 TCP 之间的公平性。
时延也从 FIFO 的 UDP 815 ms / TCP 约 350–415 ms 降到 425 / 306 ms。

**4. 但 FqCoDel 的隔离不是完全的**，两个实测事实需要如实记录：
- UDP 拿到 0.9120 Mbps（统一窗口），明显高于三流均分（≈0.66）：它始终满负荷
  排队，而 TCP 流受窗口与确认时钟约束、并非时刻有包在 qdisc 中，
  空缺份额被持续积压的 UDP 吸收（此为与调度机制一致的解释，
  未做逐包调度追踪，属推断层面的归因）。
- 设备队列在两种策略、所有组别下平均占用都在 87–88 包——qdisc
  之下那层不受 AQM 管辖的 FIFO 仍然存在并串联混合所有流（D5
  结论的复现），这是 C/FqCoDel 时延仍停留在 300–425 ms 而不是
  CoDel 目标量级的结构性原因。

### 审计 1：吞吐之和为何超过 2 Mbps——口径问题，不是数据错误

逐流跨度口径下 C 组两运行的速率之和为 2.1079（FIFO）与 2.0491
（FqCoDel）。逐流核查（rxBytes / firstTx / lastRx / 跨度 / 速率）：

| 运行 | 流 | rxBytes | firstTx | lastRx | 跨度 s | 跨度口径速率 |
|---|---|---|---|---|---|---|
| C/FIFO | tcp1 | 38,916 | 1.0000 | 3.2419 | 2.2419 | 0.1389 |
| C/FIFO | tcp2 | 41,856 | 1.0000 | 11.9934 | 10.9934 | 0.0305 |
| C/FIFO | udp | 2,631,052 | 1.0021 | 11.8597 | 10.8576 | 1.9386 |
| C/FqCoDel | tcp1 | 741,576 | 1.0000 | 11.9952 | 10.9952 | 0.5396 |
| C/FqCoDel | tcp2 | 742,752 | 1.0000 | 11.9999 | 10.9999 | 0.5402 |
| C/FqCoDel | udp | 1,253,984 | 1.0021 | 11.3513 | 10.3492 | 0.9693 |

原因：每条流的分母是它自己的收发跨度。速率是"强度量"，分母不同
的强度量之和不受链路容量约束——tcp1 的字节集中在 2.24 s 内交付，
其速率相当于"在它活跃的那段时间里"的平均强度。**没有调整任何
分母去凑数**；审计新增的是定义明确的统一窗口口径：窗口取同一
运行内所有流的最早 firstTx 到最晚 lastRx（约 10.76–11.00 s），
每条已接收的字节都必然在这段时间内穿过瓶颈，因此统一窗口速率
之和必 ≤ 2 Mbps。实测六组之和为 1.9734–1.9915 Mbps，全部满足
（差额为链路空闲间隙与未计入 IP 字节的链路层开销）。两口径下
的逐流速率：

| 运行 | 口径 | tcp1 | tcp2 | udp | 合计 |
|---|---|---|---|---|---|
| C/FIFO | 跨度 | 0.1389 | 0.0305 | 1.9386 | 2.1079 |
| C/FIFO | 统一窗口 | 0.0283 | 0.0305 | 1.9146 | 1.9734 |
| C/FqCoDel | 跨度 | 0.5396 | 0.5402 | 0.9693 | 2.0491 |
| C/FqCoDel | 统一窗口 | 0.5393 | 0.5402 | 0.9120 | 1.9915 |

（A、B 四组两口径差异很小：各流跨度本就接近，统一窗口合计
1.9801–1.9869，逐流数据见 d7_unified_window.csv。）

### 审计 2：修正后的 Jain 指数

| 运行 | jain_tcp 跨度 | jain_tcp 统一窗口 | jain_all 跨度 | jain_all 统一窗口 |
|---|---|---|---|---|
| A/FIFO | 0.9998 | 0.9998 | 0.9998 | 0.9998 |
| A/FqCoDel | 0.9995 | 0.9995 | 0.9995 | 0.9995 |
| B/FIFO | 1.0000 | 1.0000 | 0.9654 | 0.9578 |
| B/FqCoDel | 0.9999 | 0.9999 | 0.9681 | 0.9582 |
| C/FIFO | 0.7093 | **0.9987** | 0.3920 | 0.3539 |
| C/FqCoDel | 1.0000 | 1.0000 | 0.9192 | 0.9347 |

唯一实质性修正是 C/FIFO 的 jain_tcp（见分析 2 的修正说明）：
两条 TCP 的**交付量**几乎相同，跨度口径的 0.7093 度量的是交付
时间分布（一條流早早收到全部字节后沉默，另一条细水长流）。
其余各组两口径结论一致。公平性结论今后以统一窗口口径为准。
注意 C/FqCoDel 的 UDP 统一窗口速率 0.9120 仍高于三流均分
（≈0.66），分析 4 中"UDP 高于均分"的观察在更严格口径下依然
成立，其归因仍属推断。

### 审计 3：队列数据的来源与口径（逐项核实自源码）

| 项目 | 来源/方式 |
|---|---|
| qdisc 采样对象 | R0 瓶颈出口设备的根 QueueDisc（经 TrafficControlLayer 读回）；占用 = `QueueDisc::GetCurrentSize()`（FqCoDel 为各子队列之和） |
| 设备队列采样对象 | 同一 PointToPointNetDevice 的 `GetQueue()`（DropTailQueue）；占用 = `GetNPackets()` |
| 采样周期 | 首样在 t=0.01 s，之后每 10 ms 一次，至 t<12.0 s，共 **1199 样**（六组日志与 CSV 已交叉核对一致） |
| 平均占用 | 样本算术平均。**注意**：采样窗含业务启动前约 1 s 的空队列期，六组同口径、组间可比，但绝对值被同等稀释 |
| qdisc 丢弃 | `QueueDisc::GetStats()` 的总丢弃（入队+出队丢弃聚合，含 CoDel 丢弃） |
| 设备队列丢弃 | QueueBase 计数 `GetTotalDroppedPackets()`；六组实测恒为 **0** |
| 结束残留 | 仿真结束后 `GetCurrentSize()` + `GetNPackets()`；六组残留全部位于设备队列（qdisc_end 恒为 0） |

三个机制的事实/推断分界：
- **Fq 公平调度效果**——事实：C/FqCoDel 下两条 TCP 吞吐在双口径
  下均相等、UDP 被压到约 0.91–0.97；推断：将其归因于 FqCoDel 的
  按流 DRR 调度（未采集子队列级调度/丢弃计数，未做源码级追踪）。
- **CoDel 延迟控制效果**——事实：A/B 组 FqCoDel 的 qdisc 平均占用
  1.2–1.3 包 vs FIFO 的 51–57 包，时延低约 40%；推断：把时延下降
  归因于 CoDel 的排队时间丢弃——FIFO 对照组同时缺少 FQ 调度，
  两机制在本设计中不可分离（D5 单流对照为旁证）。
- **设备队列积压影响**——事实：设备队列六组平均占用 82–89 包、
  残留全在该层、其丢弃恒为 0；推断：该层 FIFO 混合削弱 qdisc 隔离
  并构成时延地板——与全部计数一致，但未做"移除该层"的对照实验
  （D5 的 devq 场景为单流旁证）。

### 审计 4：结束对账复核（含 TCP 口径说明）

六组逐一复核：未接收总数 = qdisc 丢弃 + 设备队列丢弃（恒 0）+
结束残留 + 在途余数，恒等式全部成立且余数在 [0, 未接收] 内
（FIFO 组余数 0，FqCoDel 组余数 6）。无重复计数：qdisc 丢弃的包
不会到达设备队列，两层计数不相交；残留按结束时刻队列内容计，
与丢弃不相交。另有一项交叉验证：**六组中逐流 lostPackets 之和
与瓶颈处两层丢弃计数逐一精确相等**（如 C/FIFO 2459 = 2459）——
计数证据支持瓶颈 QueueDisc 是主要可观测丢弃位置（接入链路在本
实验中无丢弃记录），两个独立计数体系互相印证。

TCP 的口径须知：FlowMonitor 统计的是 **IP 层包**——每次重传是
一个独立的 tx 包；一个报文段首次被丢、重传后交付，记 lost=1，
但应用层数据完整无缺。因此 TCP 的 lostPackets/丢失率**高估**应用
层损失；rxBytes 含每包 40 B 的 IP/TCP 头且可能计入重复交付，
高于 PacketSink 的应用层 goodput。本项目全部吞吐为 IP 层口径，
与 D3 起的定义一致，跨组比较有效，但不可直接当作应用吞吐引用。

## 校验

- run_fairness_experiments.py 内置 7 项校验全 PASS：行数与流集合
  （16 行逐流数据 / 6 行汇总）、队列读回与请求策略一致、指标非负、
  百分比范围、rx+lost≤tx、Jain 指数在 [1/n, 1]、整矩阵复跑逐行一致。
- 原 D6 回归（scripts/run_regression.sh）14 项全部 PASS，
  D4/D5 的 CSV 与保存结果逐字节一致，历史基准未被触碰。

## 结论边界（未解决的问题）

1. 单一默认随机种子：结果确定性已验证，但没有多 seed 统计重复性。
2. FqCoDel 的 Target/Interval、Quantum 参数未做敏感性扫描；
   UDP 份额高于均分的归因（分析 4）未经逐包追踪证实。
3. qdisc 丢弃计数是全队列聚合值，未按流拆分（FqCoDel 内部子队列
   计数未采集）——"UDP 的包主要死在自己的子队列"是由逐流
   lostPackets 数字推得，不是 qdisc 计数器直接读数。
